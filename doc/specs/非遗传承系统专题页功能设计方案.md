# 非遗传承系统专题页功能设计方案

## 1. 背景与目标

当前项目已经具备新闻资讯、非遗项目展示、传承人介绍、技艺视频、活动信息、沉浸体验、个人中心等基础能力，整体已经形成了较完整的前后端业务框架。但从内容组织方式来看，现有页面仍主要以“列表页 + 详情页 + 功能页”为主，内容分散在不同入口和模块中，缺少围绕某一具体主题进行集中展示、统一表达和连续引导的页面载体。

在现有结构下，用户虽然可以逐个浏览新闻、非遗项目、传承人或视频内容，但较难围绕某一个非遗主题形成系统性认知。例如，用户可能在首页看到某个非遗项目，在列表中看到相关传承人，在视频区看到相关技艺展示，在沉浸模块中接触体验内容，但这些信息之间缺少统一的组织关系，页面之间更多是并列存在，而不是围绕一个主题进行聚合表达。

从项目展示层面看，当前系统更像一个“功能集合型应用”，已经具备较丰富的模块和数据能力，但仍缺少一个能够集中体现文化叙事、视觉表达、内容聚合与产品特色的核心展示页面。对于竞赛答辩、成果展示、重点内容运营和后续迭代来说，这一能力具有较高价值。

如果后续继续在没有统一方案的情况下临时增加专题页面，容易出现以下问题：

1. 首页、详情页、活动页等页面继续承担过多内容组织职责，页面边界不清晰。
2. 专题内容关系由前端直接硬编码拼接，后续维护成本高。
3. 专题与现有非遗、传承人、视频、活动、AR 等模块之间缺少统一绑定关系，无法形成稳定复用。
4. 后续若需要做节庆活动专题、重点项目专题、地区文化专题时，容易重复开发页面逻辑。
5. 缺少统一的数据结构与接口设计，不利于后续管理和扩展。

本方案目标如下：

1. 建立一个围绕单一主题进行内容聚合、文化表达和功能串联的专题页能力。
2. 将非遗项目、传承人、技艺视频、新闻资讯、活动信息、沉浸体验等内容围绕同一主题进行组织。
3. 提升项目整体展示效果，使系统从“功能展示”进一步增强为“内容展示 + 文化叙事 + 互动体验”的综合平台。
4. 为竞赛答辩、成果演示、首页推荐和后续专题运营提供统一页面载体。
5. 第一阶段优先完成可展示、可复用、可落地的专题页基础能力，第二阶段再增强配置化和运营化能力。

## 2. 总体设计原则

### 2.1 核心原则

1. 专题页以主题聚合为核心，不替代现有详情页，而是在现有详情页之上提供更高层级的内容组织能力。
2. 专题页优先复用现有业务数据和已有模块，避免重复建设非遗、传承人、视频、活动等内容实体。
3. 前端负责页面展示、模块编排与交互跳转，后端负责专题数据聚合、内容绑定与统一输出。
4. 第一阶段优先实现“能展示、能跳转、能复用、能演示”，不一次性设计复杂的低代码专题引擎。
5. 专题页既要兼顾文化表达和视觉展示，也要兼顾后续维护和功能扩展。

### 2.2 分层思想

整体建议分为四层：

1. 前端展示层：负责专题页渲染、交互、卡片展示和页面跳转。
2. 后端聚合层：负责专题详情查询、内容聚合、关联数据组装和统一返回。
3. 内容关系层：负责维护专题与非遗、传承人、视频、活动、新闻、AR 项目的绑定关系。
4. 运营扩展层：负责后续专题推荐、专题统计、节庆活动配置和专题运营能力。

## 3. 页面定位与适用场景

### 3.1 页面定位

专题页不是普通详情页，也不是简单列表页，它承担的是“围绕某一个主题将多种内容统一组织和呈现”的作用。

专题页适合用于展示如下类型内容：

1. 某一个重点非遗项目专题
2. 某一个地区非遗文化专题
3. 某一个传统节庆活动专题
4. 某一类技艺或文化门类专题
5. 某一位代表性传承人延展专题

### 3.2 与现有页面的区别

现有页面分工建议如下：

1. 首页：负责推荐、导流、入口汇总和重点信息曝光。
2. 列表页：负责批量浏览、筛选和分页查看。
3. 详情页：负责单一对象的基础信息展示。
4. 专题页：负责将多个对象围绕同一主题统一组织、讲述和串联。

### 3.3 业务价值

专题页具备如下价值：

1. 对竞赛答辩而言，专题页可以作为项目亮点页面，集中体现文化内容组织能力。
2. 对产品展示而言，专题页可以增强系统的叙事性和视觉完整性。
3. 对后续开发而言，专题页可以成为首页推荐、节庆活动、重点内容推广的承载页。
4. 对内容复用而言，专题页可以在不新增大量基础实体的情况下，实现现有内容的重新组织。

## 4. 总体页面结构设计

专题页建议采用“主题头图 + 导语说明 + 分区模块 + 相关推荐”的结构组织方式。

### 4.1 头图区

头图区用于展示专题主视觉、专题标题、副标题和核心标签，承担页面第一屏文化氛围建立和主题识别作用。

建议展示内容：

1. 专题封面图
2. 专题标题
3. 专题副标题
4. 地域标签、类型标签或推荐标签

### 4.2 导语区

导语区用于用简洁文字说明该专题的背景、文化价值、历史来源或现实意义，让用户在进入专题页后快速理解该主题的核心内容。

建议内容形式：

1. 主题简介
2. 背景说明
3. 文化价值摘要

### 4.3 重点非遗项目区

该区域用于聚合和展示与当前专题最核心的非遗项目内容，建议优先关联现有 `heritage` 数据。

建议展示内容：

1. 项目封面图
2. 项目名称
3. 项目摘要
4. 跳转至 `heritageDetail`

### 4.4 代表性传承人区

该区域用于展示与当前专题密切相关的传承人信息，帮助用户理解技艺背后的代表性人物和传承链条。

建议展示内容：

1. 传承人头像或图片
2. 姓名与简介
3. 擅长领域或代表技艺
4. 跳转至传承人详情页或传承人列表页

### 4.5 技艺视频区

该区域用于展示与专题主题相关的技艺展示视频、工艺讲解视频或过程演示视频，增强页面可看性和沉浸感。

建议展示内容：

1. 视频封面
2. 视频标题
3. 时长或简要描述
4. 跳转至视频播放页或视频列表页

### 4.6 新闻与活动区

该区域用于展示与当前专题相关的新闻资讯、活动信息或近期动态，增强专题页的“正在发生”属性。

建议展示内容：

1. 相关新闻
2. 主题活动
3. 报名入口或跳转入口

### 4.7 沉浸体验推荐区

如果当前专题涉及已有沉浸或 AR 资源，则建议在专题页中加入沉浸体验推荐模块，将内容展示与互动体验进行连接。

建议展示内容：

1. 体验项目封面
2. 项目简介
3. 跳转至 `ARPlay` 或 `ARProjectList`

### 4.8 底部相关推荐区

该区域用于在专题尾部为用户继续提供相关专题、相关非遗项目或更多内容入口，形成浏览闭环。

## 5. 总体流程

### 5.1 用户访问流程

1. 用户从首页推荐位、Banner、活动入口或其他内容入口进入专题页。
2. 前端根据 `topicId` 或 `topicCode` 请求专题详情接口。
3. 后端根据请求参数查询专题基础信息和绑定关系。
4. 后端聚合专题关联的非遗项目、传承人、视频、新闻、活动和 AR 内容。
5. 后端返回专题页统一结构数据。
6. 前端按专题页面结构进行渲染。
7. 用户在专题页中继续跳转到详情页、列表页、活动页或沉浸体验页面。

### 5.2 后端处理流程

1. 接收专题详情请求。
2. 校验专题是否存在、是否启用、是否在有效期内。
3. 查询专题主表信息。
4. 查询专题与各类内容的绑定关系。
5. 分别查询非遗、传承人、视频、新闻、活动、AR 等关联数据。
6. 按页面模块分组装专题详情响应对象。
7. 返回统一响应结构给前端。

## 6. 数据模型设计

第一阶段建议新增 2 张核心表，用于支撑专题页能力。

### 6.1 专题主表

表名建议：

- `topic_page`

#### 6.1.1 设计目标

该表用于维护专题本身的基础信息，包括标题、封面、导语、状态和展示顺序等。

#### 6.1.2 建议字段

- `id`
- `topic_code`
- `topic_title`
- `sub_title`
- `cover_image`
- `intro_text`
- `content_text`
- `status`
- `sort_order`
- `start_time`
- `end_time`
- `create_time`
- `update_time`
- `remark`

#### 6.1.3 SQL 草案

```sql
CREATE TABLE topic_page (
  id BIGINT NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  topic_code VARCHAR(64) NOT NULL COMMENT '专题编码',
  topic_title VARCHAR(128) NOT NULL COMMENT '专题标题',
  sub_title VARCHAR(255) DEFAULT NULL COMMENT '专题副标题',
  cover_image VARCHAR(500) DEFAULT NULL COMMENT '专题封面图',
  intro_text VARCHAR(1000) DEFAULT NULL COMMENT '专题导语',
  content_text TEXT COMMENT '专题正文或补充内容',
  status CHAR(1) NOT NULL DEFAULT '0' COMMENT '状态(0启用 1停用)',
  sort_order INT DEFAULT 1 COMMENT '排序值',
  start_time DATETIME DEFAULT NULL COMMENT '生效开始时间',
  end_time DATETIME DEFAULT NULL COMMENT '生效结束时间',
  create_time DATETIME DEFAULT NULL COMMENT '创建时间',
  update_time DATETIME DEFAULT NULL COMMENT '更新时间',
  remark VARCHAR(500) DEFAULT NULL COMMENT '备注',
  PRIMARY KEY (id),
  UNIQUE KEY uk_topic_code (topic_code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='专题页主表';
```

### 6.2 专题内容绑定表

表名建议：

- `topic_content_binding`

#### 6.2.1 设计目标

该表用于建立专题与现有内容对象之间的绑定关系，实现专题页对已有内容的复用与分区展示。

#### 6.2.2 建议字段

- `id`
- `topic_id`
- `content_type`
- `content_id`
- `section_type`
- `sort_order`
- `status`
- `create_time`
- `update_time`
- `remark`

#### 6.2.3 字段说明

- `content_type` 建议值：
  - `HERITAGE`
  - `INHERITOR`
  - `VIDEO`
  - `NEWS`
  - `ACTIVITY`
  - `AR_PROJECT`

- `section_type` 建议值：
  - `HERITAGE_SECTION`
  - `INHERITOR_SECTION`
  - `VIDEO_SECTION`
  - `NEWS_SECTION`
  - `ACTIVITY_SECTION`
  - `AR_SECTION`

#### 6.2.4 SQL 草案

```sql
CREATE TABLE topic_content_binding (
  id BIGINT NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  topic_id BIGINT NOT NULL COMMENT '专题ID',
  content_type VARCHAR(32) NOT NULL COMMENT '内容类型',
  content_id BIGINT NOT NULL COMMENT '内容对象ID',
  section_type VARCHAR(64) NOT NULL COMMENT '页面分区类型',
  sort_order INT DEFAULT 1 COMMENT '排序值',
  status CHAR(1) NOT NULL DEFAULT '0' COMMENT '状态(0启用 1停用)',
  create_time DATETIME DEFAULT NULL COMMENT '创建时间',
  update_time DATETIME DEFAULT NULL COMMENT '更新时间',
  remark VARCHAR(500) DEFAULT NULL COMMENT '备注',
  PRIMARY KEY (id),
  KEY idx_topic_id (topic_id),
  KEY idx_content_type (content_type),
  KEY idx_content_id (content_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='专题内容绑定表';
```

## 9. 与现有模块关系设计

专题页不应重复建设现有内容模块，而应作为现有模块之上的聚合层。

建议关系如下：

1. `topic_page` 负责描述专题本身。
2. `topic_content_binding` 负责描述专题与具体业务内容的绑定关系。
3. `heritage`、`inheritor`、`video`、`activity`、`news`、`ARProject` 仍作为各自内容事实来源。
4. 专题页通过绑定关系实现内容复用，不修改原业务表主结构。
5. 当后续新增新的内容类型时，只需要扩展绑定关系枚举和聚合查询逻辑，不需要重构整个专题页架构。

## 11. 安全与维护设计

### 11.1 基本要求

1. 专题页只允许展示启用状态专题。
2. 专题绑定内容若已停用或删除，不应在前端继续展示。
3. 后台管理必须保留专题创建时间与更新时间。
4. 图片、视频、封面等资源地址统一走项目已有静态资源访问方式。
5. 接口输出字段结构应保持稳定，避免前端频繁适配。

### 11.2 接口校验要求

1. 请求的专题 ID 或专题编码必须有效。
2. 已停用专题不可对外展示。
3. 超出有效期的专题默认不展示。
4. 绑定关系失效时，后端应自动过滤对应内容。

## 12. 统计与运营视角

专题页建设完成后，后续可基于访问与内容数据支持如下运营分析：

### 12.1 按专题统计

1. 专题访问次数
2. 专题跳转次数
3. 专题停留时长
4. 专题内模块点击分布

### 12.2 按内容统计

1. 专题内非遗项目点击量
2. 专题内传承人点击量
3. 专题内视频播放量
4. 专题内活动报名转化情况

### 12.3 按推荐位统计

1. 首页专题入口点击率
2. Banner 专题跳转点击率
3. 不同专题推荐位的访问转化效果

## 13. 第一阶段实施范围

### 13.1 第一阶段目标

先完成一个可展示、可联调、可复用的专题页基础能力，用于竞赛展示和后续迭代基础建设。

### 13.2 第一阶段范围

1. 新建 `topic_page` 表。
2. 新建 `topic_content_binding` 表。
3. 实现专题详情接口 `GET /api/topic/{id}`。
4. 前端新增专题页 `pages/topicPage/`。
5. 首页增加专题入口或专题推荐位。
6. 支持专题绑定非遗项目、传承人、视频、活动、新闻中的至少 3 类内容。
7. 保证专题页可从首页进入并完成内容展示与页面跳转。

## 14. 第二阶段增强方向

1. 支持专题列表页和专题推荐轮换。
2. 支持专题模板化配置。
3. 支持节庆活动专题与限时专题能力。
4. 支持专题浏览统计与后台分析能力。
5. 支持更复杂的图文混排和模块排序配置。
6. 支持专题与 AR、学习中心、用户互动能力进一步联动。

## 15. 对项目整体的收益

本方案实施后，将对当前项目带来如下收益：

1. 使现有分散内容具备围绕主题统一表达的能力。
2. 强化项目在竞赛展示中的文化叙事和页面亮点。
3. 提升首页推荐、活动推广和重点内容运营的承接能力。
4. 在不破坏现有模块结构的前提下，提升系统扩展性和内容复用能力。
5. 为后续更多专题化、节庆化、活动化页面提供统一实现路径。

## 16. 最终结论

本方案的核心落点如下：

1. 专题页不替代现有详情页，而是承担更高层级的主题聚合与内容组织职责。
2. 专题页通过复用现有非遗、传承人、视频、活动、新闻和沉浸体验模块，实现多内容统一组织。
3. 使用 `topic_page` 维护专题基础信息，使用 `topic_content_binding` 维护专题与内容对象的绑定关系。
4. 前端新增专题页，后端提供专题聚合接口，形成完整的前后端落地链路。
5. 第一阶段优先完成可展示、可联调、可演示的专题页能力，第二阶段再增强配置化和运营化能力。

该设计适合作为项目后续重点内容展示、专题运营和竞赛展示的标准功能方案。
